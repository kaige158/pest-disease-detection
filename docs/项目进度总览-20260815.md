## 三、本次会话工作（2026-08-15）

### 主题：数据契约一致性修复 ✅

对 AI 服务 ↔ Spring Boot 业务后端之间的字段传递做了全链路审计，发现并修复了 **3 类"多源不一致"问题**，共 **5 处代码改动**：

| # | 问题 | 影响 | 修复 |
|:--:|------|------|------|
| 1 | `need_expert_review` 在 parser / confidence_manager / Spring Boot 三处重复计算，阈值互相冲突（<0.90 / <0.70 / 死代码） | 专家审核触发逻辑不可靠 | 统一为 confidence_manager 单一来源，删除重复计算 |
| 2 | `provider` 字段在 Spring Boot 硬编码为 `"gemini"` | 切换 Kimi/Claude 后入库记录错误 | 改为读取 AI 服务返回值 |
| 3 | `confidence_level` 在 Spring Boot 重复计算 3 级分级 | 与 AI 服务的 4 级策略（含 reject）不一致 | 改为读取 AI 服务返回值 |

**验证结果：**

| 项 | 结果 |
|------|:--:|
| Python 语法检查 | ✅ 通过 |
| Spring Boot 编译 | ✅ `EXIT=0` |
| Flutter Web 构建（蔬菜版） | ✅ `√ Built build\web` |
| UI 浏览器预览 | ✅ `localhost:8081` 正常返回 |

> **价值说明：** 这是"工程质量"层面的打磨。修复前系统虽能跑通，但数据契约存在隐性裂缝——一旦切换 Provider 或做专家审核，会产生脏数据。修复后字段有唯一数据源，为后续 Sprint 12 的 V3 Prompt 激活（需改输出格式）打好了基础。

## 六、数据闭环（AI数据飞轮）

```
Flutter拍照 → 图片质量检测 → Gemini AI识别 → 置信度策略分级
     ↓
diagnosis_record 全字段入库（原始响应+解析结果+置信度+Provider+耗时）
     ↓
用户反馈(✅/❌) → POST API → 入库
     ↓
专家审核 → evaluation_record
     ↓
训练数据就绪 → Benchmark评估 → 训练数据导出
     ↓
未来：训练专属农业视觉模型（Gemini教师 → YOLO学生）
```

**核心理念：** 使用越多 → 数据越多 → AI越准 → 价值越高。核心资产不是APP，而是农业数据。

## 二、系统架构（谁负责什么）

```
┌──────────────────┐   ①登录/注册/资料   ┌──────────────────────┐
│  Flutter APP     │ ──────────────────▶ │  Spring Boot 业务后端 │
│  蔬菜版 / 果树版  │   Bearer JWT 令牌    │  :8080               │
│                  │ ──────────────────▶ │  · 用户/鉴权          │
│  · 登录/注册页    │   ②拍照识别(multipart)│  · 识别记录入库       │
│  · 我的(个人中心) │                     │  · 知识库/审核        │
│  · 识别/知识库    │                     │  · AI 配置管理        │
└──────────────────┘                     └──────────┬───────────┘
                                                    │ ③带"当前生效AI通道"转发
┌──────────────────┐   ④表单登录(会话)              ▼
│  管理后台网页     │ ──────────────────▶ ┌──────────────────────┐
│  :8080/admin     │                     │  FastAPI AI 服务      │
│  · AI 配置中心    │                     │  :8000               │
│  · 用户管理       │                     │  · Provider 抽象      │
│  · 审核/知识库    │                     │  · 质量检测/置信度     │
└──────────────────┘                     └──────────────────────┘
```

**关键设计：AI 配置只有一份来源**

管理员在后台改配置 → 存 `core.ai_provider_config` 表 → Spring 每次调用 AI 服务时把
**当前生效通道**随请求下发 → AI 服务用这份配置构建 Provider。

> 为什么不让 AI 服务直连数据库读配置：那样会有两份配置来源、还要处理连接与缓存失效。
> 现在 AI 服务是**无状态执行器**，配置变更天然立即生效，也不需要在 AI 服务里保管密钥。

## 三、启动方式

### 3.1 本地演示（H2 内存库，无需 Docker）

```powershell
cd F:\lao-cn-APP\spring-backend
mvn -B spring-boot:run "-Dspring-boot.run.profiles=demo"
```
- 管理后台：http://127.0.0.1:8080/admin/login → `admin` / `admin123`
- 数据在内存中，**重启即清空**（仅用于演示）

### 3.2 生产（PostgreSQL）

```powershell
# 1) 建表（首次部署执行一次）
psql -U postgres -d laos_agri -f database/init.sql
psql -U postgres -d laos_agri -f database/v5_user_admin_ai_config.sql
psql -U postgres -d laos_agri -f database/seed_data_v1.sql      # 24 种病虫害

# 2) 注入环境变量后启动（Linux 用 export，Windows 用 $env:）
$env:SPRING_DATASOURCE_URL="jdbc:postgresql://localhost:5432/laos_agri"
$env:SPRING_DATASOURCE_USERNAME="postgres"
$env:SPRING_DATASOURCE_PASSWORD="<你的密码>"
$env:JWT_SECRET="<32位以上随机串>"
$env:AI_KEY_SECRET="<32位以上随机串>"
$env:ADMIN_INIT_PASSWORD="<管理员初始密码>"
mvn -B spring-boot:run
```

### 3.3 APP 构建

```powershell
cd F:\lao-cn-APP\flutter_app

# 蔬菜版（真机，指向你的服务器）
flutter build apk --release -t lib/main_vegetable.dart `
  --dart-define=API_BASE_URL=http://<服务器IP>:8080/api/v1

# 果树版
flutter build apk --release -t lib/main_fruit.dart `
  --dart-define=API_BASE_URL=http://<服务器IP>:8080/api/v1,`  # 注意：实际不换行
```
详细地址规则见 `docs/api-endpoint-config.md`。

## 四、生产环境必须配置的环境变量

| 变量 | 作用 | 不配置的后果 |
|------|------|-------------|
| `JWT_SECRET` | 签发登录令牌的密钥 | 用开发默认值，任何人都能伪造令牌 |
| `AI_KEY_SECRET` | 加密数据库里 AI Key 的主密钥 | 用开发默认值；**换机器后旧密文解不开** |
| `ADMIN_INIT_PASSWORD` | 管理员初始密码 | 每次启动随机生成并打印在日志里 |
| `SPRING_DATASOURCE_*` | 数据库连接 | 连不上库 |
| `AI_SERVICE_URL` | AI 服务地址 | 默认 `http://localhost:8000` |

> ⚠️ **`AI_KEY_SECRET` 一旦设定就不要改**：它是加密 AI Key 的主密钥，
> 改了以后数据库里已存的密文全部解不开，需要在后台重新填写 API Key。

## 五、用户使用说明（可转给老师/农户）

### 5.1 农户（APP）

| 操作 | 步骤 |
|------|------|
| 首次使用 | 点「我的」→「登录 / 注册」→ 输入手机号 + 自设密码（≥6 位）→ 自动创建账号 |

| 退出 | 「我的」→「退出登录」 |

### 5.2 管理员（后台）

| 操作 | 步骤 |
|------|------|
| 登录后台 | http://<服务器>:8080/admin/login → admin / 初始密码 |

| 管用户 | 「用户管理」→ 搜索/筛选 → 停用（该用户立即被踢下线）/ 改角色 / 重置密码 |

## 八、排障速查

| 现象 | 原因 | 处理 |
|------|------|------|
| APP 提示"无法连接服务器" | 地址不对/防火墙 | 看启动日志 `[LaosAgri] spring=...`；放行 8080/8000 |
| 后台登录页打不开 | 服务未启动 | `mvn spring-boot:run` 看日志 |
| **后台点「登录」没反应** | 已于 2026-09-26 修复：原 `login.html` 表单 `action` 指向 `/admin/dashboard` 且输入框没有 `name`，认证从未触发 | 已改为 POST `/admin/login` + `name="username"/"password"`，并新增错误提示 |
| **后台密码错误但页面无提示** | 同上，模板未处理 `?error=1` | 已新增红色错误横幅与重置指引 |
| **表格「操作」列按钮文字空白** | 已于 2026-09-26 修复：JS 的 i18n 键列表漏了 `disable`/`enable`/`changeRole`/`resetPassword`，取到空字符串 | 已补齐，并加了缺键自检（控制台会报错而不是静默空白） |
| **「状态」列显示空白** | 字符串拼接把 class 与文案混在一起 | 已修复为「正常 / 已停用」 |
| **改了 HTML/JS 却没生效** | 静态资源从 `target/classes` 读取，未重新编译；且浏览器缓存旧 JS | 改完执行 `mvn compile`；已加 `?v=` 版本参数与 `resources.cache.period: 0` |
| **忘记管理员密码** | 无短信/邮件通道 | 执行 `scripts\reset_admin_password.ps1 -Password 新密码`（仅本机可用） |
| 后台登录提示"账号不存在" | 管理员未初始化 | 查看启动日志里的初始化信息；或设 `ADMIN_INIT_PASSWORD` 后重启 |
| 启动即失败，日志有「启动被拒绝」 | 密钥缺失/过弱 + 严格模式 | 执行 `scripts\generate_secrets.ps1` 生成 `.env` |
| 识别报"仅支持 jpg/png/webp" | 图片格式 | 客户端已限制为相机/相册图片 |
| 识别返回"AI识别服务不可用" | AI 服务或 Key 有问题 | 后台「AI 配置中心」点「测试连接」看具体报错 |
| 改了 AI Key 后识别仍失败 | 未点「设为当前生效」 | 生效通道是单独操作的 |
| 换服务器后 AI Key 解不开 | `AI_KEY_SECRET` 变了 | 用原密钥，或在后台重新填写 Key |
| **用户/识别记录重启后消失** | 演示档用 H2 内存库 | 改用 PostgreSQL（生产配置，见 3.2） |

## 八之二、管理员密码与登录（补充说明）

**默认账号**：`admin` / `admin123`（演示档由 `application-demo.yml` 的 `app.admin-init-password` 写入）

**忘记密码**（仅本机可执行）：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\reset_admin_password.ps1 -Password 你的新密码
```

该脚本调用后端 `POST /api/v1/ops/reset-password`，接口有三重限制：

1. 只接受来自 `127.0.0.1` / `::1` 的请求，远程调用直接 403
2. 需要运维令牌 `app.ops-token`（演示档默认 `local-dev-reset-token`）
3. 生产环境把 `app.ops-token` 留空即**关闭该接口**，届时改用数据库直接改密码：

```sql
-- 生产环境无接口时的兜底做法
-- 1) 生成 BCrypt 哈希（可在任意有 Java 环境处用以下方式生成）
--    或用后台「用户管理」页对任意用户执行「重置密码」
-- 2) 直接更新
UPDATE core."user" SET password_hash = '<bcrypt-hash>', token_version = token_version + 1
WHERE phone = 'admin';
```

> 提示：只要还能登录后台，**用「用户管理」页的重置密码功能最方便**——不需要脚本、也不需要动数据库。

## 十、管理后台产品化补强（2026-09-26 追加）

依据实际使用反馈，对后台做了 4 项改造，均已实测通过。

### 10.1 首次登录提醒修改密码

| 项 | 说明 |
|---|---|
| 数据 | `core."user".must_change_password` 字段 |
| 置位时机 | 管理员账号初始化、被管理员重置密码、被运维脚本重置密码 |
| 清除时机 | 用户自行改密成功后 |
| 界面 | 所有后台页面顶部弹出黄色横幅「请立即修改初始密码」+「立即修改」按钮 |
| 改密页 | `/admin/change-password`（服务端表单，含两次输入一致性校验） |
| 改密后 | 递增 `token_version` → 本次会话立即失效，需用新密码重新登录 |

### 10.2 后台中老双语（可交接给老挝本地人员）

- **文案**：`i18n/messages_zh.properties` + `i18n/messages_lo.properties`（约 150 条），
  以 `#{key}` 在模板中使用；缺失的 key 自动回退中文
- **语言优先级**：`?lang=xx` 参数 → 账号 `language_pref` → Cookie → 浏览器
- **切换入口**：登录页与侧边栏底部都有「中文 / ລາວ」按钮；
  切换会**写回账号**，因此在另一台电脑登录也是同一语言
- **覆盖范围**：全部 8 个后台页面（仪表盘/审核/知识库/AI配置/用户/统计/登录/改密）
- **JS 文案**：通过页面隐藏元素 `#i18n` 的 `data-*` 属性由服务端注入，
  不需要在 JS 里再维护一份多语言字典

### 10.3 手机号国际化

| 项 | 说明 |
|---|---|
| 数据 | 新增 `country_code` 字段；`phone` 只存本地号码 |
| 唯一性 | 口径改为 **(区号 + 本地号码)**：`+856 20xxxx` 与 `+66 20xxxx` 是两个账号 |
| 支持国家 | 老挝+856（默认）/ 中国+86 / 泰国+66 / 越南+84 / 柬埔寨+855 / 缅甸+95 / 美加+1 / 日+81 / 韩+82 / 澳+61 |
| 校验 | 本地号码 6~15 位；兼容 `+856...`、`856...`、`020...` 三种写法自动识别区号 |
| 接口 | `GET /api/v1/auth/countries?language=zh` 下发国家列表（公开接口，登录前即可用） |
| APP | 登录页手机号框左侧为可点击的区号选择器，默认 🇱🇦 +856 |
| 后台 | 用户管理列表按 `+区号 号码` 展示，便于区分国家 |
| 历史数据 | `country_code` 为空即视为未拆分的老数据，登录/展示按原样处理，不受影响 |

**短信验证码：暂未启用**。原因：老挝本地短信通道不稳定且需额外采购，
首版用「手机号+密码」已能完整跑通用户体系。
接入时只需替换 `AuthService.loginOrRegister` 的凭据校验环节，
新增 `/auth/sms/send` 与 `SmsSender` 接口实现即可，**数据与界面无需改动**。

### 10.4 仪表盘显示真实账号（不再写死"老师"）

- 移除硬编码的「👩‍🏫 老师 | 欢迎回来」
- 改为显示**当前登录账号的昵称 + 角色**（角色名走 i18n）
- 老挝语界面下若昵称是纯中文，自动回退显示账号名，
  避免老挝同事看到看不懂的中文

## 十一、本次追加的业务规则变更（重要）

## 十三、手机号归属验证与角色权限（2026-09-26 追加）

依据用户反馈的 4 个问题做了修复，均已实测。

### 13.1 手机号国家识别修复

**问题**：中国手机号注册后被标记为 `+856`（老挝）。

**根因**：APP 固定发送默认国家 `856`，后端因此**从不做号码识别**，一律按老挝建档。
更糟的是早期实现用"区号前缀匹配"，`13900001111` 会被误读成「美国 +1 39…」。

**修复**：改为**按各国号码书写形态识别**（每个国家一个正则），并让号码本身的信息优先于界面默认值。

| 输入 | 修复前 | 修复后 |
|------|--------|--------|
| `13900001111` | `+856` ❌ | `+86` ✅ |
| `13900001111`（前缀匹配版） | `+1` ❌ | `+86` ✅ |
| `02055551234` | `+856` | `+856` ✅ |
| `+8613900001111` | — | `+86` ✅ |

**关于歧义**：泰国 `0812345678` 这类号码形态上与老挝难以区分。
系统不再"猜"，而是标出可能存在歧义（`others` 非空），
**APP 需让用户显式选择国家** —— 这正是原问题的核心：
不应假定"用户没选国家就是老挝"。

### 13.2 短信验证码（防止假账号堆积）

**问题**：密码是用户自设的，**号码却无法验证** —— 任何人编一个格式合法的号码就能注册，
造成假账号淹没后台。

**策略**（兼顾安全与农户体验）：

| 场景 | 是否要验证码 | 原因 |
|------|:--:|------|
| 新号码注册 | **必须** | 假账号的主要来源 |
| 老账号 + 密码正确 + 同一设备 | 不需要 | 农户日常使用不能每次都收短信 |
| 老账号 + 密码正确 + **换设备** | **必须** | 显著提高盗号门槛 |

**系统如何知道"是不是第一次"** —— 三个信号，全部由后端自己判断，APP 无需猜：

| 信号 | 存在哪里 | 作用 |
|------|----------|------|
| 该 `(区号, 手机号)` 是否有用户记录 | `core.app_user`（唯一索引 `uk_user_country_phone`） | 有 = 老账号，没有 = 首次注册 |
| `device_uuid` 是否与上次登录一致 | `core.app_user.last_device_uuid` | 一致 = 可信设备，不一致 = 换设备 |
| 密码是否正确 | `password_hash`（BCrypt） | 密码错 → 直接拒绝，不发验证码（否则等于给攻击者免费发短信） |

**交互契约**（APP 只需按返回码走，不需要事先查"我是不是新用户"）：

```
POST /api/v1/auth/login            → 200 直接登录（老账号 + 可信设备 + 密码正确）
                                   → 428 需要验证码（新号码 或 换设备）
POST /api/v1/auth/sms/send         → 200 已下发；429 触发限流
POST /api/v1/auth/login {smsCode}  → 200 登录成功，并把这台设备记为可信设备
GET  /api/v1/auth/detect-country   → 号码属于哪个国家（无副作用，不发短信）
```

`GET /auth/detect-country?phone=0205555123` 返回：

```json
{ "country_code": "856", "country_name_zh": "老挝", "flag": "🇱🇦",
  "confidence": "matched",          // explicit=用户写了+86 / matched=形态吻合 / guessed=形态对不上
  "others": ["855"],                // 其它同样吻合的国家
  "ambiguous": true,                // true = 界面应让用户显式选国家，别替他决定
  "local_number": "0205555123" }
```

用途：① 登录页边输边提示"这看起来是中国号码，是否切换区号"；
② 自动化验证可以稳定测识别规则（不依赖发短信，因而不受发送限流影响）。

`device_uuid` 由 APP 首次启动时随机生成并本地持久化
（`lib/core/auth/device_identity.dart`），**与手机号无关**，
所以同一台手机换个号码登录也算"可信设备"，不会重复要验证码。

> 结论：**不需要每次登录都收短信**。只有"新号码注册"和"换手机登录"两种情况要，
> 老用户在同一台手机上天天用不会被短信打扰 —— 这也是为老挝短信通道不稳定留的余地。

**防刷设计（短信要花钱，必须限流）**：

| 维度 | 限制 |
|------|------|
| 同一号码 | 60 秒 1 条 / 1 小时 5 条 / 1 天 10 条 |
| 同一 IP | 1 小时 20 条（识别批量刷号） |
| 全平台 | 1 天 2000 条（兜底，防刷爆费用） |
| 尝试次数 | 每条码最多 5 次（6 位码 ≈ 二十万分之一） |

**安全实现**：数据库只存验证码的 **SHA-256 哈希**，不存明文；有效期 5 分钟；用后即废。

**短信通道**：抽象为 `SmsSender` 接口。当前默认 `LoggingSmsSender`（只打日志，不真发），
接入老挝本地服务商时新增一个实现类即可，**登录逻辑不用改**。

> ⚠️ 开发/演示期通过 `/api/v1/auth/sms/demo-code` 取验证码（受 `app.sms.expose-code` 控制）。
> **生产环境必须把 `SMS_EXPOSE_CODE` 设为 false**，并把 `SMS_REQUIRE_CODE` 设为 true。

### 13.3 管理员查看完整手机号（二次验证 + 审计）

列表默认只显示脱敏号码（`+86 1390****111`）。需要完整号码时：

1. 点「查看手机号」→ 弹出对话框
2. **输入当前管理员自己的登录密码**

### 13.4 四级角色权限（原先只有 ADMIN 生效）

**用户提问**："四个角色有什么用处？有没有赋予特殊权限？"
排查结论：**早期只有 ADMIN 真正生效**，其余三个只是数据库里的标签。现已落地权限矩阵：

| 功能 | ADMIN | EXPERT | TECHNICIAN | FARMER |
|------|:--:|:--:|:--:|:--:|
| 进入后台 | ✅ | ✅ | ✅ | ❌ |
| 仪表盘 / 数据统计 | ✅ | ✅ | ✅ | ❌ |
| AI 审核（查看+提交） | ✅ | ✅ | ✅ | ❌ |
| 知识库（增删改） | ✅ | ✅ | ❌ 只读 | ❌ |
| 用户列表（查看） | ✅ | ✅ | ✅ | ❌ |
| 停用/改角色/重置密码 | ✅ | ❌ | ❌ | ❌ |
| 查看完整手机号 | ✅ | ❌ | ❌ | ❌ |
| AI 配置（查看） | ✅ | ✅ | ❌ | ❌ |
| AI 配置（修改密钥） | ✅ | ❌ | ❌ | ❌ |

**设计理由 —— 职责分离**：
- **ADMIN** 是技术/运营负责人，管密钥与账号安全
- **EXPERT（老师）** 管内容与审核，但**碰不到 API Key 和用户账号**
- **TECHNICIAN（农技员）** 只读 + 审核，**不能改知识库**，
  避免未经审核的内容直接进入农户看到的界面
- **FARMER** 只能用 APP

实现方式：角色继承（`ADMIN > EXPERT > TECHNICIAN`）避免到处重复写角色列表；
后端 `@PreAuthorize` 强制校验，**前端按角色隐藏无权菜单**（避免"点了报 403"的困惑）。

> ⚠️ URL 级权限在 `SecurityConfig` 中配置。若把 `security.admin-open` 设为 true
> （仅本地演示用），后台会**完全放开**，生产环境必须保持 false。

**界面上也能看懂（本次新增）**：后台「用户管理」页顶部有可折叠的
**《角色权限说明》** 面板，11 项功能 × 4 个角色的 ✓/— 矩阵 + 每个角色一句话定位；
点任意用户的「改角色」时，弹窗里会**实时显示该角色的"可以做 / 不可以做"清单**。

> 关键：界面说明不是另写一份文案，而是由后端 `Permission.matrix()` **实时生成**
> （见 `config/AdminPermissionView.java`）。改了权限规则，界面说明自动跟着变，
> 不会出现"界面写着能改、代码却拦住"的最难排查的不一致。

（字段 `demo_code`）—— 由 `app.sms.expose-code` 控制，演示档为 true：

### 13.7 删除用户账号（只删账号，数据资产全部保留）

用户要求："用户删除功能，删除相关的内容一起，并且删除需要管理员、并且需要登录密码"。

**接口**（两个都是 `@PreAuthorize("hasRole('ADMIN')")`，EXPERT/TECHNICIAN 一律 403）：

```
GET  /api/v1/admin/users/{id}/delete-preview   删除影响预览（不发密码，只读）
POST /api/v1/admin/users/{id}/delete           { "password": "管理员自己的登录密码" }
```

**只删"人"，绝不删"数据"** —— 平台核心资产是农业数据，每删一个账号就挖掉一块资产是不可接受的：

| 处理 | 对象 | 说明 |
|------|------|------|
| **删除** | `core.app_user` 账号本身 | 手机号、密码哈希、昵称、区号、设备记录随之消失，号码可被重新注册 |
| **删除** | `core.phone_verification` 该号码的验证码记录 | 纯个人信息残留，无数据价值 |
| **匿名保留** | `core.diagnosis_record` | 只清 `user_id` / `device_uuid` / `device_info`；作物、AI 结果、专家审核结论、图片、地区全部保留 |
| **保留** | `extension.training_dataset` 训练数据资产 | 一个字都不动，含专家已确认的标签 |
| **保留** | `extension.disease_image` 图片记录 + 磁盘文件 | 训练与溯源的原始素材 |
| **保留** | `core.audit_log` | 谁在什么时候删了谁，必须可追溯 |

> 为什么清 `device_uuid`：它是设备级持久标识，能跨账号把同一个人认出来，属于个人信息；
> 而它对"这张叶子是什么病"没有任何价值，所以一并清掉 —— 去掉"是谁"，留下"是什么"。

界面把**「将删除」和「将保留」分成两个色块**展示（保留项用绿色，并写明是匿名保留），
管理员点确认前就能确认"平台数据不会少"。

删完会在审计里留一条：
`DELETE_USER ... 识别记录匿名保留=1、图片保留=0、训练资产保留=0，删除验证码=1`。

**四道闸门**：

1. 角色必须是 ADMIN（类级注解放开了 EXPERT/TECHNICIAN 查看用户列表，删除单独收紧）
2. 必须再次输入**管理员自己的登录密码**（`BCrypt` 校验）——
   仅靠"已登录"不够：管理员离开座位时浏览器可能还开着
3. 不能删自己（否则当前会话立刻失效）、不能删最后一个管理员
4. 成功 / 密码错误 / 被拦下，三种情况都写审计日志，便于发现异常探测

### 13.8 审计日志页面（让"记入审计日志"这句话可查证）

新增 `GET /api/v1/admin/audit-logs`（仅 ADMIN）与后台「审计日志」页（侧边栏，仅 ADMIN 可见）。
列出最近的敏感操作：`DELETE_USER` / `DELETE_USER_FAILED` / `DELETE_USER_BLOCKED` /
`REVEAL_PHONE` / `REVEAL_PHONE_FAILED`，含操作人、对象、详情、来源 IP、时间。
危险操作在列表里用红色/橙色标签区分，便于在长列表里一眼找到。

> 只读，不提供修改与删除接口 —— 审计日志的价值就在于不可篡改。

### 13.9 顺带修掉的一个数据隐患

老挝号码有两种写法：`02055550001`（本地习惯）与 `2055550001`（系统展示时用的形态）。
原先登录查找只补 0、不去 0，于是**用 `2055550001` 注册的账号，改用 `02055550001` 登录会查不到**，
系统会当成新号码**再注册一个重复账号**，用户数据从此分裂。
现在两种写法互为候选（`PhoneCodec.lookupCandidates`），指向同一个账号。

### 13.10 上传图片修了两个真问题（做删除功能时发现的）

1. **图片其实没存到 uploads 目录**：`MultipartFile.transferTo(相对路径)` 在 Tomcat 下是相对
   *multipart 临时目录* 解析的，不是相对进程工作目录 —— 目录建在 `./uploads/recognition`，
   文件却写进临时目录并在请求结束后消失，表现为"有 image_url 但磁盘上找不到图"。
   已改为**绝对路径**写盘（`app.storage.upload-dir`，默认 `./uploads`）。
2. **`/uploads/**` 没有对外映射**：数据库里有图片路径，浏览器/APP 打开却 404。
   新增 `WebResourceConfig` 把该前缀挂到磁盘目录，并在 `SecurityConfig` 里放行
   （APP 用 `<img src>` 加载图片不会带 Bearer 令牌；文件名由服务端随机生成，不可枚举）。

### 13.11 做删除功能时挖出来的 5 个接口 500（已修）

验证删除功能时顺手把所有管理接口跑了一遍，发现**审核中心、数据统计、训练数据统计等
一整组接口在运行时直接 500**。这些正是"对平台有益的数据功能"，必须修：

| # | 问题 | 根因 | 影响 | 修法 |
|---|------|------|------|------|
| 1 | `AdminController` 全部接口 500 | `@PreAuthorize("... or ${security.admin-open:false}")` —— **`${}` 占位符在 SpEL 里不生效**，每次调用抛 `SpelParseException` | 待审核列表、审核提交、训练统计、评估准确率、数据统计全挂 | 改为引用 Bean：`or @securityFlags.adminOpen`（新增 `SecurityFlags`） |
| 2 | 数据统计页 500 | `default_schema: PUBLIC`（demo），而原生 SQL 写的是 `core.crop` | `core.crop` 不存在 | demo 改为 `default_schema: core`，与生产一致 |
| 3 | 同上 | 原生 SQL 表名未限定 schema（`FROM disease_image` / `disease` / `knowledge_article`） | 按连接默认 schema 解析，PostgreSQL 默认 `search_path` 也不含 core | 全部补上 `core.` 前缀 |
| 4 | 准确率接口 500 | 评估表为空时 `SUM(...)` 返回 **NULL**，代码直接 `.longValue()` → NPE | 新部署一看统计页就崩 | SQL 加 `COALESCE(...,0)` + Java 侧 `toLong()` 兜底 |
| 5 | 准确率接口 500 | `expert.evaluation_record` 只有 SQL 没有 JPA 实体，demo（Hibernate 建表）里这张表根本不存在 | demo 下评估统计不可用 | 补 `EvaluationRecord` 实体 + `CREATE SCHEMA expert` |

> 生产配置也一并修了：`application.yml` 打开 `hibernate.default_schema: core`。
> 之前这行是注释掉的，而 `init.sql` 把业务表都建在 `core` 下 ——
> `ddl-auto=validate` 在 PostgreSQL 上启动时会因为找不到表而失败。

修完实测：8 个管理接口全部 200（此前 5 个是 500）。

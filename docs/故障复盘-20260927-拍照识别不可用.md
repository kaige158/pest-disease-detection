# 故障复盘：拍照识别 100% 失败（2026-09-27，香港 ECS 首次真机联调）

> 一句话结论：**不是模型的问题，也不是网络的问题 —— 是图片质量检测把整张照片变成 Python 列表，
> 瞬间申请约 0.8GB 内存，把只有 700MB 上限的 AI 容器打到进程被杀。**
> 该缺陷从代码写下的第一天就存在，但所有单元测试都用小图，所以一直绿着。

## 1. 现象（用户视角）

- 手机 APP 点「拍照识别」→ 无论拍什么、传什么照片，**100% 失败**，提示"AI识别服务暂时不可用"。
- 服务器上 `docker logs laos_ai` **看不到任何识别请求**，只有启动那几行日志。
- 后台「AI 配置中心」点「测试连接」**却是成功的**（因为那是文本对话，不是图片）。
- AI 容器 `RestartCount` 一路上涨（每传一张照片 +1），但 `OOMKilled=false`。

## 2. 排查过程（可复用的方法）

| 步骤 | 做法 | 得到的关键信息 |
|---|---|---|
| 1 | 手机报错从"AI服务暂时不可用"改为**透传 AI 层原始错误** | 看到 `Error while extracting response ... content type [application/octet-stream]` —— 说明 Spring 收到了**非 JSON 的响应**，不是"连不上" |
| 2 | 在 Spring 容器里 `printenv AI_SERVICE_URL`、`getent hosts ai-service`、`curl -i http://ai-service:8000/nope` | 地址/ DNS / AI 服务**全都正常**，且 `GET /nope` 在 AI 日志里**有记录** → 说明日志功能正常，是 POST 大 body 不出现在日志里 |
| 3 | 用**小 body** 和**大 body（3.4MB，真实照片量级）**分别 POST，`curl -sv` 看完整响应头 | 小 body：`422` + JSON + 日志正常；大 body：`100 Continue` → **`Empty reply from server`**，紧接着服务 **Connection refused** |
| 4 | `docker inspect laos_ai --format '{{.State.FinishedAt}} {{.RestartCount}}'` | 进程死亡时间**正好等于**大 body 请求的那一刻，`RestartCount` 同步 +1 |
| 5 | 本地对同一张图做内存剖析（`tracemalloc`） | 300 万像素图：旧代码峰值 **206MB**，按语料 1200 万像素放大 **≈0.8GB**（容器上限 700MB）；新代码 **2MB** |

**方法论要点：**
- 先分清"**连不上**"、"**连上了但返回看不懂**"、"**连上了、返回正常但结果不对**"三种情况 —— 报错文本不同，排查方向完全不同。
- 大 body / 小 body **分别试一次**，是最快区分"网络问题"与"业务代码问题"的手段。
- 容器"日志里没有这条请求"不等于"请求没到达"：进程在写出访问日志之前就死了，日志自然没有。
  要用 `RestartCount` / `FinishedAt` 这类**容器状态**来交叉验证。
- 「测试连接」通过 ≠ 图片识别可用：**文本接口和视觉接口是两条路**。

## 3. 根因

`ai-service/app/services/quality/image_quality_checker.py`：

```python
pixels = list(gray.getdata())     # 灰度：每像素 1 个对象
pixels = list(img.getdata())      # RGB ：每像素 1 个 **三元组**
```

对一张 4000×3000（1200 万像素）的真实照片，RGB 那一句会构造 1200 万个 tuple，
峰值 **≈0.8GB** → 撞上 `mem_limit: 700m` → 内核杀进程 → 客户端收到被截断的响应。

> 顺带解释了另一个诡异现象：Spring 报的 `content type [application/octet-stream]`
> 是**连接被中途截断后**客户端拿到的残缺响应，并不是 AI 服务真的返回了二进制流。
> （我们的 AI 服务在任何代码路径下都不可能返回 octet-stream，这本身就是一条排查线索。）

## 4. 修复

| 编号 | 修复内容 | 关键文件 |
|---|---|---|
| ① | 所有逐像素统计**只在缩略图上做**（分析图长边 512px / 植被统计 128px）；亮度改用 `ImageStat`（C 层直方图，不搬像素进 Python） | `image_quality_checker.py` |
| ② | 植被判定从 `g > r+b` 改为农业标准 **ExG(2G−R−B)>20**（见下节实测数据） | 同上 |
| ③ | 发给模型前统一压缩到长边 1200px（原图 base64 3~5MB，很多厂商直接 413） | `ai_providers/base.py`（基类共用），OpenAI 兼容通道 / Kimi / Gemini 全部走同一份 |
| ④ | 新增**内存红线回归测试**：`check()` 处理 600 万像素图，峰值 >60MB 直接失败 | `ai-service/tests/test_image_quality_memory.py` |
| ⑤ | 新增**真实语料校准工具**：可对任意语料目录跑批量检测并打印内存峰值/等级分布 | `ai-service/tools/check_corpus_quality.py` |
| ⑥ | 缺 API Key 时给出人话提示，不再抛 `Illegal header value b'Bearer '` | `ai_providers/base.py::_require_api_key` |
| ⑦ | 质量不合格的结构化错误翻译成人话（`图片质量不合格：图片模糊(清晰度12)。建议：请对焦清晰后拍摄`） | `AiServiceClient.java` |

### 用真实语料校准的结果（老师提供的 117 张照片）

| 指标 | 旧规则 | 新规则（ExG>20） |
|---|---|---|
| "绿色占比"中位数 | **0.00**（每张真实照片都被判成"没拍到植物"） | **77.6%** |
| 等级分布 | 几乎全部 poor | good=101 / poor=16 / reject=3 |
| 3 张 reject 是什么 | —— | 深色信息图海报（`蔬菜.jpg` 1272×2800，亮度 32），**剔除正确** |

内存：117 张全量检测 **10.2 秒**，进程峰值 **130 MB**（上限 700MB）。

## 5. 同批次修掉的另外两个"必然失败"缺陷

| 缺陷 | 影响 | 说明 |
|---|---|---|
| 识别/助手请求**没有下发** `provider_config` | 后台点「设为当前生效」对识别**完全无效**，AI 服务一直用自己 .env 的默认值 | 新增 `AiRuntimeConfigService`，每次调用下发当前生效通道（含解密后的 Key，只走内存、不落日志） |
| AI 服务 `/api/v1/chat` 调用了**未定义的** `get_ai_provider()` | AI 助手每次 `NameError` → 500，Spring 又把它吞成"AI服务暂时不可用" | 改为与 `/identify` 一致的 `build_provider(ProviderConfig.from_dict(request.provider_config))` |

## 7. 教训（写进开发规范）

1. **任何"逐像素"的 Python 循环，只允许跑在缩略图上。** 原图尺寸的照片在 Python 里是"GB 级对象"，不是"几 MB 文件"。
2. **测试数据必须有"真实尺寸"这一档。** 只用小图/构造图测试，会漏掉整整一类内存缺陷。
3. **生产环境的资源上限（mem_limit / 超时 / 包体上限）要能在本地复现。** 本次校准工具就是用 `docker run --memory 700m` 复现生产上限跑的。
4. **错误信息要一路透传到最外层。** 这次能定位，靠的就是把 AI 层的原始报错、HTTP 状态、响应体前 300 字都带出来；此前每层都"兜底成一句友好提示"，等于把线索全部销毁。
5. **"测试连接通过"要标明测的是什么。** 后台界面已写明各通道是否支持图片识别，避免"测试通过、识别不了"。

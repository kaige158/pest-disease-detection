### 3.2 用户系统：手机号验证与国际号码

| 议题 | 处理方式 |
|------|---------|
| 假账号堆积 | **首次注册必须短信验证**；老账号 + 同一设备 + 密码正确可免验证码；**换设备必须重新验证** |
| 短信通道未接入 | 抽象 `SmsSender` 接口，默认只打日志；接入老挝本地服务商只需新增一个实现类，**登录逻辑不用改** |
| 防刷短信费用 | 同号码 60秒/1小时5条/1天10条，同IP 1小时20条，全平台1天2000条，验证码只存 SHA-256 哈希 |
| 中国号码被标成 +856 | 改为按**号码书写形态**识别国家，形态有歧义时标记 `ambiguous` 交由用户显式选择，不再"猜" |
| 号码两种写法分裂账号 | `02055550001` 与 `2055550001` 现互为候选，指向同一账号（修复前会重复注册） |

### 3.3 管理员系统：四级角色权限 + 可审计

| 角色 | 后台能看到什么 | 关键约束 |
|------|---------------|---------|
| **ADMIN 平台管理员** | 全部页面 + 用户管理 + AI 密钥 | 可停用/改角色/重置密码/删除账号/查看完整手机号 |
| **EXPERT 农业专家（老师）** | 仪表盘 / 审核 / 知识库(可改) / AI配置(只读) / 统计 | **碰不到账号与密钥**（职责分离） |
| **TECHNICIAN 农技员** | 仪表盘 / 审核 / 知识库(只读) / 统计 | 不能改知识库，避免未审核内容进用户端 |
| **FARMER 农户** | 只能用 APP | 访问后台一律 403 |

**本次新增的三项运营能力**：

1. **角色权限说明界面** —— 后台「用户管理」页顶部有 11×4 的权限矩阵，改角色弹窗里实时列出
   该角色"可以做 / 不可以做"。说明文案由后端权限矩阵**实时生成**，不会与真实拦截逻辑脱节。
2. **删除用户账号** —— 仅 ADMIN、需再次输入管理员登录密码；**只删账号与个人信息，
   识别记录 / 图片 / 训练数据资产全部匿名保留**（平台核心资产一条不少）。
3. **审计日志页** —— 谁在什么时候删了谁、看了谁的手机号，成功与失败都留痕，只读不可篡改。

### 3.4 AI 配置中心

- 支持通道：**Gemini / DeepSeek / Kimi / OpenAI / Claude / 自定义(OpenAI 兼容)**，均可后台新增与切换
- API Key 采用 **AES-256-GCM 加密入库**，界面只显示脱敏串，接口**绝不回传明文**
- 配置只有一份来源：Spring 管理配置表 → 随请求下发给无状态的 AI 服务 → **改完即生效**

## 六、数据闭环（AI数据飞轮）—— 并说明"为什么不能删数据"

```
农户拍照 → 质量检测 → AI识别 → 置信度分级 → diagnosis_record 全字段入库
     ↓
用户反馈(✅/❌) → 专家审核 → evaluation_record（准确率统计）
     ↓
专家确认 → training_dataset（training_ready）→ 导出训练集
     ↓
未来：训练专属农业视觉模型（Gemini教师 → YOLO学生）
```

> **本次特别落实的一条原则：删除用户账号时，绝不删除数据资产。**
> 删账号只删"人"（手机号/密码/昵称/验证码记录），识别记录**匿名保留**（清空 `user_id`/`device_uuid`），
> **训练数据资产与图片一字不动**。界面上把"将删除"与"将保留"分成两个色块展示，
> 管理员点确认前就能确认平台数据不会少。

## 九、本次修复的缺陷（含 5 个严重 500）

做删除功能时把所有管理接口跑了一遍，发现**审核中心、数据统计、训练数据统计等一整组接口在运行时直接 500**：

| # | 问题 | 根因 | 影响 |
|:--:|------|------|------|
| 1 | `AdminController` 全部接口 500 | `@PreAuthorize` 里写了 `${security.admin-open:false}` —— **`${}` 占位符在 SpEL 中不生效**，每次调用抛 `SpelParseException` | 待审核列表、审核提交、训练统计、评估准确率、数据统计全挂 |
| 2 | 数据统计页 500 | 演示档 `default_schema: PUBLIC`，而原生 SQL 写的是 `core.crop` | `core.crop` 不存在 |
| 3 | 同上 | 3 处原生 SQL 表名未限定 schema | 按连接默认 schema 解析，**PostgreSQL 默认 search_path 也不含 core，生产同样会挂** |
| 4 | 准确率接口 500 | 评估表为空时 `SUM(...)` 返回 NULL，代码直接 `.longValue()` → NPE | 新部署一看统计页就崩 |
| 5 | 准确率接口 500 | `expert.evaluation_record` 只有 SQL 没有 JPA 实体 | demo（Hibernate 建表）里这张表根本不存在 |
| 6 | **上传图片其实没落盘** | `MultipartFile.transferTo(相对路径)` 在 Tomcat 下按 multipart 临时目录解析，文件写进临时目录后消失 | "有 image_url 但磁盘上找不到图" |
| 7 | **`/uploads/**` 没有对外映射** | 数据库有路径，浏览器/APP 打开 404 | 识别结果图片无法显示 |
| 8 | 生产启动隐患 | `hibernate.default_schema: core` 被注释掉，而 `init.sql` 把表建在 core 下 | `ddl-auto=validate` 在 PostgreSQL 上启动失败 |

**修复后实测：8 个管理接口全部 200（此前 5 个为 500）**，并已把这 7 个接口纳入 `verify_roles.py` 回归，防止再次静默失效。
